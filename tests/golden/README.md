# Golden tfvars fixtures

`tfvars-full.json` and `tfvars-tier1.json` were generated by the Neo4j-backed parser
(`scripts/neo4j_parser.py --scope=full|tier1` at commit 790c34e) for the CSVs recorded in
`source.json`. The topology model that replaced Neo4j (`scripts/topology.py`)
reproduces them byte for byte, and must keep doing so. The CSVs were later normalized
(`topology.dump()`: no BOM, LF line endings, no unnamed columns, shortest float form) without
changing the output, so `source.json` records the hash of the normalized files.

```bash
python -m unittest tests.test_golden_tfvars
```

The test skips if the CSVs no longer match `source.json`.

Neo4j is gone, so fixtures are now regenerated with the parser itself, starting from a commit
where the test passes. Regenerate them in the same commit as the change to the CSVs or the
generator, so the fixture diff shows exactly what that change did to the tfvars:

```bash
python scripts/generate_tfvars.py --scope=full --base=grayspace/2026.11 --output-file=tests/golden/tfvars-full.json
python scripts/generate_tfvars.py --scope=tier1 --base=grayspace/2026.11 --output-file=tests/golden/tfvars-tier1.json
```

Then update `source.json`: `csv_sha256` (`sha256sum *.csv | sha256sum`, run in the CSV directory), the commit, and `generated_by`.

## Output order is part of the contract

The parser's Cypher queries had no `ORDER BY`, so rows came back in the order Neo4j's query plan
walked the graph, and `scripts/topology.py` reproduces that order. It matters: vnets are named
`v100`, `v101`, … by a counter as links are processed, so a different link order renames every
vnet, and Terraform would replace the networks of a running deployment. The rules below were
checked against both fixtures. "Reversed" means Neo4j returned a node's relationships newest
first, i.e. in reverse CSV row order.

| Output | Order |
|---|---|
| `routers` (both scopes) | ISPs in `isps.csv` order; within each ISP, its routers in reverse `routers.csv` order |
| Links, full scope | Locations in `locations.csv` order; for each location, the routers located there in reverse `located_in.csv` order; for each such router, the connections *ending* at it in reverse `connections.csv` order |
| Links, tier1 scope | ISPs in `isps.csv` order; for each ISP, its routers in reverse `operated_by.csv` order; for each, the connections ending at it in reverse `connections.csv` order |
| `core_dns`, `core_ca`, `locations` | CSV order |

In `networks`, the 218 links come first, then 105 customer networks in router order, then the 4
core CA networks. Clients are not yet characterized; the test will catch any difference.

Changing these orders later is a deliberate migration (stable vnet names, or Terraform `moved`
blocks), not a cleanup.
